# 03 · Domain model

---

## 1 · Identifier conventions

Human-readable, prefixed, sortable. Never expose a bare UUID in the UI.

| Entity | Format | Example |
|---|---|---|
| Incident | `INC-YYMMDD-NNNN` | `INC-260916-0417` |
| Assignment | `ASG-<incident seq>-<n>` | `ASG-0417-2` |
| Unit | `<kind><nn>` | `AMB-14`, `MRU-03`, `PRV-221`, `FIRE-07` |
| Station | `STN-<agency>-<nn>` | `STN-DCAS-12` |
| Hospital | `HOS-<nn>` | `HOS-04` |
| Zone | `Z-<level><nn…>` | `Z-E1` emirate, `Z-S03` sector, `Z-C0147` community |
| Advisory | `ADV-YYMMDD-NNN` | `ADV-260916-012` |
| User | `<rolecode>-<4 hex>` | `DSP-4A1C`, `RSP-9F02`, `CIT-71BE` |
| Scenario run | `RUN-YYMMDD-NNN` | `RUN-260916-003` |
| Makani | 10 digits, displayed as two groups of five | `2797 87586` |

Internally every table also carries a `uuid` primary key. The readable id is a unique
column, generated by the server, and is what appears in the UI, in exports and in logs.

## 3 · State machines

### 3.1 Incident

```
   reported ──► triaged ──► dispatched ──► responding ──► on_scene
                   │             │              │            │
                   │             │              │            ├──► transporting ──► at_hospital ──► closed
                   │             │              │            └──► resolved_on_scene ─────────────► closed
                   │             │              └──► reassigned (back to dispatched)
                   │             └──► cancelled ──────────────────────────────────► closed
                   └──► non_emergency ──────────────────────────────────────────► closed
```

`closed` carries an `outcome`: `transported` · `treated_released` · `refused` ·
`deceased` · `false_alarm` · `duplicate` · `cancelled_by_caller` · `no_patient_found`.

**The seven measured stages** — every one of these is a real timestamp, not derived:

| Stage | From → to | Column pair | ISO 22320 KPI |
|---|---|---|---|
| 1 Call handling | `reported_at` → `triaged_at` | | Call answer + triage time |
| 2 Dispatch decision | `triaged_at` → `dispatched_at` | | Dispatch time |
| 3 Acknowledge | `dispatched_at` → `acknowledged_at` | on assignment | Unit acknowledge time |
| 4 Roll-out (chute) | `acknowledged_at` → `enroute_at` | on assignment | Turnout time |
| 5 En-route travel | `enroute_at` → `onscene_at` | on assignment | Travel time |
| 6 On-scene care | `onscene_at` → `transporting_at` | on assignment | On-scene time |
| 7 Transport | `transporting_at` → `at_hospital_at` | on assignment | Transport time |

**Response time** (the headline number) = `reported_at` → first `onscene_at` across all
assignments on the incident. This definition is written into a database view,
`v_incident_response`, so that every screen computes it identically. Disagreement
between screens on what "response time" means is the single most common failure in
systems like this.

### 3.2 Assignment

```
   offered ──► acknowledged ──► enroute ──► onscene ──► transporting ──► at_hospital ──► cleared
      │              │             │           │
      ├─► declined   │             │           └──► resolved_on_scene ──► cleared
      ├─► timed_out  │             │
      └─► cancelled ─┴─────────────┴──► cancelled
```

An `offered` assignment that is neither acknowledged nor declined within
`jurisdiction.acknowledgeTimeoutSec` (default 45) becomes `timed_out` and the dispatch
engine is re-run automatically, with the timeout recorded as a measured event — because
acknowledge-time drift is exactly the kind of finding Pillar 1 exists to surface.

> **As built (Phase 5)** — `server/domain/lifecycle.js` is the single source of these
> machines; the API refuses what it refuses, and the console renders its buttons from the
> `allowedActions` it computes.
>
> | Action | From | To | Stamps | Unit becomes |
> |---|---|---|---|---|
> | acknowledge | offered | acknowledged | `acknowledged_at` | assigned |
> | decline *(reason)* | offered | declined | `declined_at`, `decline_reason` | available |
> | timeout *(system only)* | offered | timed_out | — | available |
> | enroute | acknowledged | enroute | `enroute_at` | responding |
> | onscene | enroute | onscene | `onscene_at` — from the first position fix within 100 m when the unit reported one; `route_taken` built from its fixes | on_scene, at the entrance |
> | at_patient | onscene | onscene | `at_patient_at`, `vrt_sec` (+ predicted VRT kept beside it) | on_scene |
> | transporting *(hospital)* | onscene | transporting | `transporting_at`, `hospital_id` — refused for a unit that cannot carry a patient | transporting |
> | resolve | onscene | resolved_on_scene | — | on_scene |
> | at_hospital | transporting | at_hospital | `at_hospital_at` | at_hospital, at the hospital |
> | clear | onscene · resolved_on_scene · at_hospital | cleared | `cleared_at` | available |
> | cancel *(dispatcher, reason)* | offered · acknowledged · enroute | cancelled | — | available |
>
> - **The incident's state is derived** from its assignments after every transition
>   (most advanced live assignment wins; a cleared one counts for what it reached). With
>   no live assignment it returns to `triaged` — the "reassigned" path.
>   `first_onscene_at` / `first_at_patient_at` are the earliest across all assignments.
> - A declined, timed-out or stood-down assignment has `is_primary` set false, so
>   `v_incident_response` measures the unit that actually responded; the failed offer
>   stays in `v_assignment_stages` as a measured event.
> - **Closing** stands down pre-arrival assignments and is refused while any crew is on
>   scene, transporting or at hospital.
> - Automatic re-dispatch after a decline or timeout is capped at `maxAutoRedispatch` (2).
>
> **Schema additions (idempotent, `schema.sql` §10):** `incidents.is_resting` (the demo
> resting state, never counted as history or in KPIs); `route_cache` (OSRM results);
> `idempotency_keys`; partial index `asg_active_idx` on live assignments;
> `inc_ref_pattern_idx` for reference allocation. **View:** `mv_eta_calibration`.
>
> **References:** incidents `INC-YYMMDD-NNNN` on the GST calendar day, allocated under an
> advisory lock; assignments `ASG-YYMMDD-NNNN-n`.

### 3.3 Advisory

```
   open ──► analysing ──► acted ──► verifying ──► closed
     │                       │                      │
     └──► dismissed ─────────┴──────────────────────┘  (with a mandatory reason)
```

`acted` sets `assigned_agency_id`, `owner_user_id` and `sla_due_at`. An advisory past
its `sla_due_at` in `acted` raises an escalation. `verifying` is the re-measure window:
the advisory states a baseline and a target, and closing it requires the measured value.

### 3.4 Unit

```
   off_duty ──► available ──► assigned ──► responding ──► on_scene ──► transporting
                    ▲                                                        │
                    │                                                        ▼
                    ├──────────────── cleared ◄──── at_hospital ◄────────────┘
                    │
                    ├──► standby   (positioned at an advisory's staging point)
                    ├──► relocating
                    └──► out_of_service (maintenance / crew rest / restock)
```

CREATE TABLE assignments (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  ref         text UNIQUE NOT NULL,
  incident_id uuid NOT NULL REFERENCES incidents(id),
  unit_id     uuid NOT NULL REFERENCES units(id),
  state       assign_state NOT NULL DEFAULT 'offered',
  is_primary  bool NOT NULL DEFAULT true,

  offered_at       timestamptz NOT NULL,
  acknowledged_at  timestamptz,
  declined_at      timestamptz,
  decline_reason   text,
  enroute_at       timestamptz,
  onscene_at       timestamptz,
  transporting_at  timestamptz,
  at_hospital_at   timestamptz,
  cleared_at       timestamptz,

  hospital_id      uuid REFERENCES hospitals(id),

  -- The concept note's "route taken vs route proposed" comparison
  route_proposed      geometry(LineString, 4326),
  route_proposed_sec  int,
  route_proposed_m    int,
  route_taken         geometry(LineString, 4326),
  route_taken_sec     int,
  route_taken_m       int,

  -- "Actual against predicted arrival, so the model is held to account"
  eta_predicted_at    timestamptz,
  eta_method          text,
  eta_error_sec       int GENERATED ALWAYS AS (
                        CASE WHEN onscene_at IS NOT NULL AND eta_predicted_at IS NOT NULL
                        THEN EXTRACT(EPOCH FROM onscene_at - eta_predicted_at)::int END) STORED,

  -- Why this unit was chosen — the explainability record, kept forever
  dispatch_rationale  jsonb,

  run_id     uuid REFERENCES scenario_runs(id)
);
CREATE INDEX ON assignments (incident_id);
CREATE INDEX ON assignments (unit_id, offered_at DESC);

### 4.9 Views — the shared definitions

`server/db/views.sql`. Every screen and every engine reads these; no screen computes a
KPI from raw tables. This is how "response time" stays one number.

| View | Gives |
|---|---|
| `v_incident_response` | Per incident: the seven stage durations, total response, the responding unit, the zone, whether the target was met |
| `v_assignment_stages` | Per assignment: acknowledge, turnout, travel, on-scene, transport durations |
| `v_zone_daily` | Per zone per day: call count by kind and priority, p50/p90 response, closure rate, availability-minutes |
| `v_zone_hourly` | The same at hour granularity — the input to `demand` |
| `v_unit_utilisation` | Per unit per day: assigned minutes, available minutes, jobs, mean turnout |
| `v_agency_sla` | Per incident per agency: notified, acknowledged, elapsed, met/not-met |
| `v_eta_accuracy` | Predicted vs actual arrival, error distribution, by hour-of-week and zone |
| `v_preempt_impact` | Pre-empt events, granted rate, seconds saved vs matched non-preempted runs |
| `v_hospital_load` | ED occupancy, inbound count, mean handover time |
| `v_data_quality` | Latest quality run per source, rolled up |

## 5 · TypeScript mirror

`web/src/lib/types.ts` mirrors this model exactly. The rule: **the SQL is the source of
truth and the TypeScript follows it**, not the reverse. A generator
(`npm run types:gen`) reads `schema.sql` enums and emits the union types, so
`incident_state` in Postgres and `IncidentState` in TypeScript cannot drift.

```ts
export type IncidentState =
  | 'reported' | 'triaged' | 'dispatched' | 'responding' | 'on_scene'
  | 'transporting' | 'at_hospital' | 'resolved_on_scene' | 'cancelled'
  | 'non_emergency' | 'closed';

export interface EngineResult<T> {
  value: T;
  unit?: string;
  confidence: number;                    // 0..1
  window: { from: string; to: string };
  inputs: Array<{ source: string; rows: number; asOf: string }>;
  factors: Array<{ name: string; contribution: number; direction: 'up' | 'down' }>;
  method: string;                        // 'poisson-rate-hourly-v1'
  computedAt: string;
}
```

`EngineResult` is the type that makes the explainability requirement structural rather
than aspirational: an advisory card component takes an `EngineResult`, and there is no
way to render one without its factors and window being available.
